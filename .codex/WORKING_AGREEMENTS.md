# Working Agreements — راهنمای ادامهٔ کار برای AI Agent

## نقش و خروجی مورد انتظار

به‌عنوان Senior Frontend Designer / React Developer عمل کن. هدف ساخت یک تجربهٔ فروشگاهی فارسی، تمیز، قابل‌فهم و واکنش‌گراست، با حفظ قابلیت‌های موجود در حین بازطراحی.

## قواعد ایمن توسعه

1. قبل از تغییر، `git status`، HEAD، فایل‌های مرتبط و تفاوت با مبنای مستندات را بررسی کن.
2. مستندات این پوشه snapshot هستند؛ اگر کد تغییر کرده باشد، **کد فعلی مرجع حقیقت** است و مستندات باید به‌روز شوند.
3. ادعای اجرای تست یا مشاهدهٔ UI نکن مگر واقعاً اجرا و بررسی شده باشد.
4. بدون درخواست مالک، تغییرات مخرب، مهاجرت بزرگ framework، merge، deploy یا انتشار انجام نده.
5. هر اصلاح را کوچک، قابل بازگشت و با حداقل تغییرات غیرمرتبط انجام بده.
6. اگر موردی هنوز mock است (API، login، cart، recommendations) آن را به‌عنوان قابلیت production معرفی نکن.
7. اطلاعات احراز هویت، token یا دادهٔ حساس را در `.codex` ثبت نکن.
8. برای تغییر کد، اول ایراد چرخهٔ fetch را حل کن؛ سپس به سراغ refactor و طراحی برو.
9. هنگام افزودن کامپوننت، semantics، keyboard accessibility، alt text و RTL واقعی را رعایت کن.
10. پس از هر مرحله، تست‌های مرتبط (وقتی قابل اجرا باشند) و بررسی موبایل/دسکتاپ را گزارش کن؛ PASS فرضی نده.

## راهنمای طراحی (پیشنهاد؛ هنوز تصویب نشده)

- UI راست‌به‌چپ با متن‌های فارسی، اعداد و قالب قیمت مشخص؛ متن انگلیسی API ممکن است موقتاً باقی بماند.
- در موبایل طراحی ابتدا برای عرض کم، سپس تبلت و دسکتاپ؛ بدون ارتفاع ثابت برای تصاویر قهرمان یا کارت‌ها مگر دلیل طراحی قابل‌دفاع وجود داشته باشد.
- استفاده از `CSS Grid` یا layout انعطاف‌پذیر برای فهرست محصولات؛ media queries شفاف.
- پالت رنگ محدود، spacing scale، typography، hover/focus states و طراحی واحد برای ProductCard.
- وضعیت‌های loading, error, empty را از ابتدا در طراحی در نظر بگیر.
- انتخاب برند، رنگ اصلی، نوع فونت، امکانات خرید و هویت بصری **تصمیم‌های باز مالک** هستند؛ از ساخت واقعیت جدید پرهیز کن.

## تعریف Done برای یک تغییر

فایل‌های تغییرکرده مشخص باشند؛ رفتار و UX قبل/بعد شرح داده شود؛ build یا دلیل عدم اجرا گزارش شود؛ regressions مرتبط بررسی شوند؛ در صورت تغییر معماری، اسناد `.codex` به‌روز شوند.
